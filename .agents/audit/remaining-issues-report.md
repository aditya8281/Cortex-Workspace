## Issue 1 — P0: `logger` used but never imported in `vault.py`

**File:** `backend/app/api/v1/vault.py:113`

```python
logger.warning("Vault rate limiter Redis failure, falling back to in-memory: %s", e)
```

The `unlock_vault` function references `logger` on line 113 inside the Redis-failure `except` block, but `logger` is never imported or defined in this module. If Redis is unavailable and the rate limiter falls back, this line will raise `NameError: name 'logger' is not defined`, crashing the vault unlock endpoint.

**Fix:** Add `import logging` and `logger = logging.getLogger(__name__)` at the top of the file (after the existing imports around line 7).

**Severity:** P0 — vault unlock is broken when Redis is down

## Issue 3 — P1: `SyncTriggerResponse.job_id` is `int` but frontend expects `string`

**File:** `backend/app/schemas/model.py:242`
**Frontend type:** `frontend/src/shared/types.ts:641`

```python
class SyncTriggerResponse(BaseModel):
    job_id: int          # ← schema says int
    ...
```

The frontend `SyncJob` type declares:
```typescript
export interface SyncJob {
  job_id: string;        # ← frontend expects string
  ...
}
```

The `trigger_sync` endpoint (`models.py:379`) returns `"job_id": job.id` where `job.id` is an integer auto-generated by the database. The `response_model=SyncTriggerResponse` will serialize it as a JSON number. If the frontend tries to use this as a `string` (e.g., for URL construction), it will fail.

**Fix:** Change `job_id: int` to `job_id: str` in `SyncTriggerResponse` and cast in the endpoint: `"job_id": str(job.id)`.

**Severity:** P1 — sync trigger response type mismatch, could break sync polling

## Issue 4 — P1: `SyncStatusResponse` missing `status` and `last_sync` fields

**File:** `backend/app/api/v1/sync.py:241-248` (schema)
**Frontend type:** `frontend/src/shared/api/sync.ts:29-37`

The backend schema:
```python
class SyncStatusResponse(BaseModel):
    watching: int
    pending_changes: int
    indexed_files: int
    errors: int
    status: str
    last_sync: str | None
    watched_paths: list[dict[str, Any]]
```

The frontend type:
```typescript
export interface SyncStatus {
  watching: number;
  pending_changes: number;
  indexed_files: number;
  errors: number;
  status: string;
  last_sync: string | null;
  watched_paths: WatchedPath[];
}
```

The endpoint at line 418-426 constructs the response but `last_sync` is always `None` (hardcoded). This matches the schema but provides no useful data. **More critically**, the `watched_paths` items are constructed as dicts with `initial_scan_job_id` and `initial_scan_status` fields that the frontend `WatchedPath` type expects — these are always `None`/the `SyncState.status` string.

The schema and response match, but the `last_sync` value is never populated from `SyncState.last_sync_at`:

```python
# Line 418-426 — last_sync is hardcoded to None
return SyncStatusResponse(
    watching=watcher.watched_count,
    pending_changes=0,
    indexed_files=0,
    errors=0,
    status="watching" if watcher.is_running else "idle",
    last_sync=None,   # ← should read from SyncState.last_sync_at
    watched_paths=watched_paths,
)
```

**Fix:** Populate `last_sync` from the most recent `SyncState.last_sync_at` across user states.

**Severity:** P1 — `last_sync` is always null, `pending_changes`/`indexed_files` always 0

## Issue 5 — P1: Download queue/history endpoints missing `response_model`

**File:** `backend/app/api/v1/models.py:565-646`

Two endpoints return raw dicts without `response_model`:

1. `GET /models/downloads/queue` (line 565) — returns `{"active": [...], "queued": [...], "completed": [...], "failed": [...]}`
2. `GET /models/downloads/history` (line 615) — returns `{"history": [...]}`

The frontend types (`DownloadQueueResponse`, `DownloadJob`) expect specific field names and types. Without `response_model`, there's no automatic validation, and the OpenAPI docs are incomplete.

Additionally, the download job dicts include fields like `downloaded_bytes`, `total_bytes`, `speed_bytes_sec`, `eta_seconds`, `queue_position` that don't all match the frontend `DownloadJob` type exactly (e.g., frontend has `downloaded_bytes` and `total_bytes` which match).

**Fix:** Create Pydantic schemas for download queue/history responses and add `response_model=` to both endpoints.

**Severity:** P1 — no contract enforcement on download endpoints

## Issue 8 — P1: `RepoIndexResponse` frontend/backend field name mismatch

**File:** `backend/app/schemas/repository.py:44-49`
**Frontend type:** `frontend/src/shared/types.ts:289-295`

Backend schema:
```python
class IndexResult(BaseModel):
    files_scanned: int
    files_indexed: int
    files_skipped: int
    files_errors: int    # ← "files_errors"
    chunks_created: int
```

Frontend type:
```typescript
export interface IndexResult {
  status: string;       // ← also missing from backend
  files_scanned: number;
  files_indexed: number;
  files_skipped: number;
  // no files_errors
  chunks_created: number;
}
```

Two mismatches:
1. Backend has `files_errors` but frontend doesn't expect it
2. Frontend expects `status` but backend schema doesn't include it

The endpoint at line 188-197 returns `"status": "completed"` in the outer dict, but the inner `IndexResult` dict uses `files_errors` (matching the backend schema). The frontend `IndexResult` type doesn't have `files_errors`.

**Fix:** Either rename `files_errors` to match frontend expectations or add `status` to the schema. Also consider whether `files_errors` should be exposed to the frontend.

**Severity:** P1 — field name mismatch between backend and frontend types

## Issue 9 — P1: `AgentRunInfo.updated_at` field doesn't exist on `AgentRun` model

**File:** `backend/app/schemas/agent.py:53`
**Model:** `backend/app/models/agent.py:35-58`

The `AgentRunInfo` schema declares:
```python
updated_at: str | None = None
```

But the `AgentRun` ORM model has no `updated_at` column. The `serialize_run()` method in `run_manager.py:237-249` also doesn't include `updated_at` in its output dict. This means the field silently defaults to `None` in every API response.

The frontend `AgentRun` type doesn't include `updated_at` either, so this is technically not a frontend issue, but it's a schema/model inconsistency that could confuse API consumers.

**Fix:** Either add `updated_at` to the `AgentRun` model and populate it, or remove it from `AgentRunInfo` schema.

**Severity:** P1 — phantom field in API schema, no data ever provided
