# P01: Backend Services Reorganization — CORTEX

**Document:** Phase 01 of Version 1.01
**Authority:** Stage 6 — Master Versioned Implementation Roadmap
**Date:** 2026-06-27

---

## Objective

Move all backend services from the flat `services/` directory into domain-organized subdirectories. Establish domain ownership, prevent future import sprawl, and prepare for domain-specific evolution in v1.02+.

---

## Purpose

The current `services/` directory contains 45 flat Python files. This makes it impossible to know which domain owns which service. When a new contributor joins, they cannot answer "where does memory logic live?" without reading every file. Reorganizing into domain directories:

1. **Establishes ownership** — each domain directory has a clear boundary
2. **Prevents import sprawl** — imports become `from app.services.memory import X` instead of `from app.services import X`
3. **Enables domain evolution** — v1.02 can add domain-specific middleware per directory
4. **Reduces merge conflicts** — developers working on different domains touch different directories

### Task 1: Create Domain Service Directories

Create the following directories under `backend/app/services/`:

```
backend/app/services/
├── memory/           # Long-term memory, documents, graphs, indexing
├── awareness/        # File watching, staleness, hardware detection
├── intelligence/     # Embeddings, RAG, LLM, model catalog
├── interaction/      # Conversations, notifications, user management
├── learning/         # (empty — reserved for future adaptive learning)
├── developer/        # (empty — reserved for future dev tools)
├── utility/          # (empty — reserved for future utility services)
├── integration/      # Sync state management
├── system/           # Health checks, usage tracking, seed data
├── download/         # Model download management
└── sync/             # Synchronization service
```

Each directory gets an `__init__.py` that re-exports public symbols:

```python
# backend/app/services/memory/__init__.py
"""Memory domain services."""

from backend.app.services.memory.manager import memory_manager
from backend.app.services.memory.long_term import long_term_memory
from backend.app.services.memory.graph import graph_builder
from backend.app.services.memory.vault import vault_service

__all__ = [
    "memory_manager",
    "long_term_memory",
    "graph_builder",
    "vault_service",
]
```

**Code architecture:**
- `__init__.py` files serve as the public API for each domain
- Internal modules use relative imports within the domain
- Cross-domain imports go through `__init__.py` only (never direct module imports)
- Empty domains (`learning/`, `developer/`, `utility/`) get `__init__.py` with a docstring placeholder

**Test Criteria:**
- All 11 directories exist with `__init__.py`
- `python -c "from backend.app.services.memory import memory_manager"` works
- `python -c "from backend.app.services.intelligence import embedding_service"` works
- No circular imports detected (run `python -c "import backend.app.services"`)

**Risk Notes:**
- *Risk:* Domain boundaries are wrong. *Mitigation:* Follow `migration_map.md` exactly. If a file doesn't fit, document the exception.
- *Risk:* Empty domains are never filled. *Mitigation:* Empty domains are intentional — they document future expansion areas.

**Merge strategy for indexing files:**

The 5 indexing files (`batch_indexer`, `document_indexer`, `incremental_indexer`, `indexing_orchestrator`, `indexing_rules`) are merged into `services/memory/indexing.py`:

1. Read all 5 files to understand their interfaces
2. Create `services/memory/indexing.py` with:
   - `class IndexingOrchestrator` — main entry point (from `indexing_orchestrator.py`)
   - `class BatchIndexer` — batch processing (from `batch_indexer.py`)
   - `class DocumentIndexer` — single document indexing (from `document_indexer.py`)
   - `class IncrementalIndexer` — delta indexing (from `incremental_indexer.py`)
   - `class IndexingRules` — validation rules (from `indexing_rules.py`)
3. Move `cross_file_search.py` → `services/memory/search.py` (no merge, just move)

**Code architecture — indexing merge:**

```python
# backend/app/services/memory/indexing.py
"""Memory indexing services — consolidated from 5 original files.

Original files:
- batch_indexer.py → class BatchIndexer
- document_indexer.py → class DocumentIndexer
- incremental_indexer.py → class IncrementalIndexer
- indexing_orchestrator.py → class IndexingOrchestrator
- indexing_rules.py → class IndexingRules
"""

from backend.app.services.memory.indexing_rules import IndexingRules
from backend.app.services.memory.document_indexer import DocumentIndexer
from backend.app.services.memory.batch_indexer import BatchIndexer
from backend.app.services.memory.incremental_indexer import IncrementalIndexer
from backend.app.services.memory.indexing_orchestrator import IndexingOrchestrator

__all__ = [
    "IndexingRules",
    "DocumentIndexer",
    "BatchIndexer",
    "IncrementalIndexer",
    "IndexingOrchestrator",
]
```

**Import changes after merge:**

```python
# Before (in any consumer file)
from backend.app.services.batch_indexer import BatchIndexer
from backend.app.services.document_indexer import DocumentIndexer

# After
from backend.app.services.memory.indexing import BatchIndexer, DocumentIndexer
# Or via __init__.py
from backend.app.services.memory import BatchIndexer, DocumentIndexer
```

**Test Criteria:**
- All 14 files moved to `services/memory/`
- `git mv` used for all moves (preserves history)
- `python -c "from backend.app.services.memory import *"` works
- No original files remain in `services/` root for these 14 files
- Merge targets compile without errors

**Risk Notes:**
- *Risk:* Merge conflicts during indexing merge. *Mitigation:* Merge one file at a time. Run tests after each merge step.
- *Risk:* Lost git history after merge. *Mitigation:* Use `git mv` for the move, then merge content. History is preserved for the move, and the merge is documented in commit message.
- *Risk:* Import breakage in consumers. *Mitigation:* P03 (Import Migration) handles all consumer updates. P01 just moves files.

### Task 7: Verify Migration — Rollback Validation

After all moves, verify the migration is correct and that rollback is possible.

**Verification steps:**

```bash
# Step 1: Verify directory structure
ls backend/app/services/
# Expected: memory/ awareness/ intelligence/ interaction/ learning/ developer/ utility/ integration/ system/ download/ sync/

# Step 2: Verify no flat files remain (except __init__.py)
find backend/app/services/ -maxdepth 1 -name "*.py" -not -name "__init__.py"
# Expected: 0 results

# Step 3: Verify all domain __init__.py files exist
for dir in memory awareness intelligence interaction learning developer utility integration system download sync; do
  test -f "backend/app/services/$dir/__init__.py" && echo "OK: $dir" || echo "MISSING: $dir"
done

# Step 4: Verify import works
python -c "import backend.app.services"
echo "Import check: $?"

# Step 5: Verify git history preserved
git log --oneline --follow -- backend/app/services/memory/manager.py
# Should show history from memory_manager.py

# Step 6: Run test suite
make test

# Step 7: Verify rollback is possible
git diff --stat HEAD~1
# Should show only file moves, no content changes
```

**Rollback procedure:**

```bash
# If migration fails, rollback with:
git checkout HEAD~1 -- backend/app/services/
# This restores all service files to their original flat location
```

**Test Criteria:**
- All verification steps pass
- Rollback procedure works (tested on a branch)
- `git diff --stat` shows only renames, no content changes
- Test suite passes after migration

**Risk Notes:**
- *Risk:* Rollback doesn't work because of merge content. *Mitigation:* Commit moves first (pure renames), then commit merges separately. Rollback reverts the merge commit.
- *Risk:* Git history is lost. *Mitigation:* `git mv` preserves history. Verify with `git log --follow`.
