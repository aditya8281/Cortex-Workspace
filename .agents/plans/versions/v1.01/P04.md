# P04: Frontend Reorganization — CORTEX

**Document:** Phase 04 of Version 1.01
**Authority:** Stage 6 — Master Versioned Implementation Roadmap
**Date:** 2026-06-27

---

## Objective

Move frontend components from the flat `shared/` structure into feature-based modules. Establish clear ownership for every component and prepare for the feature-module architecture in P07.

---

## Purpose

The current frontend has all components in `shared/`. This makes it impossible to know which domain owns which component. When a new contributor asks "where does the search UI live?", they must read every file. Reorganizing into feature modules:

1. **Establishes ownership** — each feature module owns its components
2. **Enables lazy loading** — features load independently (P07 builds on this)
3. **Prevents component sprawl** — new components go in the correct feature module
4. **Aligns with backend domains** — frontend features mirror backend service domains

### Task 2: Define Feature Module Conventions

Create a conventions document that governs all feature module development.

**Target file:** `frontend/src/features/CONVENTIONS.md`

**Conventions to define:**

```markdown
# Feature Module Conventions — CORTEX Frontend

## Naming Conventions

| Item | Convention | Example |
|------|-----------|---------|
| Directory | lowercase singular | `memory/`, `search/`, `agents/` |
| Component files | PascalCase | `MemoryView.tsx`, `SearchResults.tsx` |
| Hook files | camelCase with `use` prefix | `useMemorySearch.ts` |
| Type files | camelCase | `types.ts` |
| API files | camelCase | `api.ts` |
| Test files | `<name>.test.ts` | `useMemorySearch.test.ts` |
| Fixture files | `fixtures.ts` | `fixtures.ts` |

## Export Rules

1. **Public API:** `index.ts` is the ONLY file other features import from.
2. **Internal imports:** Features may import from `@/shared/` but NOT from other `@/features/*/` directories.
3. **Type imports:** Always use `import type { X }` for type-only imports.
4. **Re-exports:** `index.ts` re-exports everything consumers need. No deep imports.

## Dependency Rules

1. **Features depend on shared, never on each other.** `features/memory/` cannot import from `features/search/`.
2. **Shared is the integration layer.** If two features need to share data, it goes in `shared/`.
3. **No circular dependencies.** Feature → Shared → Feature is forbidden.
4. **API layer isolation:** Feature `api.ts` wraps `shared/api/` calls. Features never call `apiClient` directly.

## File Structure Rules

1. **Minimum files per feature:** `index.ts`, `types.ts`, `api.ts` (3 files).
2. **Components directory:** Required if feature has UI. Empty `components/index.ts` if no components yet.
3. **Hooks directory:** Required if feature has state logic. Empty `hooks/index.ts` if no hooks yet.
4. **Tests directory:** Required. At minimum, a smoke test that verifies the feature module loads.

## Lazy Loading

1. **Every feature module is lazy-loaded** via `React.lazy()` in the router.
2. **Route definition** imports from `@/features/<feature>/index.ts`.
3. **No feature is eagerly imported** in the root layout (except shared providers).

## Code Style

1. **Functional components only** — no class components.
2. **Hooks for state** — no raw `useState` in components deeper than 1 level.
3. **Error boundaries** — each feature wraps its route in an error boundary.
4. **Suspense** — each lazy-loaded feature shows a skeleton during loading.
```

**Test Criteria:**
- `CONVENTIONS.md` exists at `frontend/src/features/CONVENTIONS.md`
- Document covers all 7 convention sections
- Examples are correct TypeScript/React
- Conventions are consistent with existing codebase patterns

**Risk Notes:**
- *Risk:* Conventions are too rigid. *Mitigation:* Document exceptions explicitly. "If a rule needs breaking, add an exception entry."
- *Risk:* Conventions are ignored. *Mitigation:* P07 Task 5 (validation) checks conventions. Future CI can lint convention compliance.

### Task 3: Move API Client Files

Verify that API clients stay in `shared/api/` (they are shared across features) and that feature-specific API wrappers go in `features/*/api.ts`.

**Current state:**

```
frontend/src/shared/api/
├── client.ts          # API client with auth, error handling
├── index.ts           # Re-exports
├── memory.ts          # Memory API calls
├── knowledge.ts       # Knowledge API calls
├── search.ts          # Search API calls
├── repo.ts            # Repository API calls
├── conversations.ts   # Conversation API calls
├── agent.ts           # Agent API calls
├── indexing.ts        # Indexing API calls
├── models.ts          # Model API calls
├── sync.ts            # Sync API calls
├── vault.ts           # Vault API calls
```

**Decision:** API clients STAY in `shared/api/` because they are shared across features. Feature-specific API wrappers (thin layers with error handling) go in `features/*/api.ts`.

|-------------|-------------|-------|

| `shared/api/knowledge.ts` | `shared/api/knowledge.ts` (stays) | Shared across features |
| `shared/api/search.ts` | `shared/api/search.ts` (stays) | Shared across features |
| `shared/api/repo.ts` | `shared/api/repo.ts` (stays) | Shared across features |
| `shared/api/conversations.ts` | `shared/api/conversations.ts` (stays) | Shared across features |
| `shared/api/agent.ts` | `shared/api/agent.ts` (stays) | Shared across features |
| `shared/api/indexing.ts` | `shared/api/indexing.ts` (stays) | Shared across features |
| `shared/api/models.ts` | `shared/api/models.ts` (stays) | Shared across features |
| `shared/api/sync.ts` | `shared/api/sync.ts` (stays) | Shared across features |

| `shared/api/index.ts` | `shared/api/index.ts` (stays) | Barrel exports |

**Code architecture — shared vs. feature API:**

```typescript
// shared/api/client.ts — SHARED (used by all features)
// This is the core API client with auth, error handling, retry logic.
// Features import from here but don't modify it.

export const apiClient = {
  get: async (url: string, config?: RequestInit) => { ... },
  post: async (url: string, data: unknown, config?: RequestInit) => { ... },
  put: async (url: string, data: unknown, config?: RequestInit) => { ... },
  delete: async (url: string, config?: RequestInit) => { ... },
};

// features/memory/api.ts — FEATURE-SPECIFIC
// Thin wrappers over shared API client with feature-specific error handling.
// This is where feature-specific logic lives.

import { apiClient } from '@/shared/api/client';
import type { MemorySearchResult } from './types';

export async function searchMemory(query: string): Promise<MemorySearchResult[]> {
  try {
    const response = await apiClient.get('/api/v1/memory/search', {
      params: { q: query },
    });
    return response.data;
  } catch (error) {
    // Feature-specific error handling
    console.error('Memory search failed:', error);
    throw error;
  }
}
```

- All shared API files remain in `shared/api/`
- No API files moved to feature modules
- `shared/api/index.ts` re-exports all API functions

**Risk Notes:**
- *Risk:* Developers move shared API files to feature modules. *Mitigation:* Conventions document (Task 2) explicitly states shared API stays in `shared/api/`.
- *Risk:* Feature API wrappers duplicate shared API logic. *Mitigation:* Feature wrappers are thin — error handling only. No business logic.
