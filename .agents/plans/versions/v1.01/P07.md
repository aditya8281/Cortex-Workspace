# P07: Frontend Feature Module Scaffolding — CORTEX

**Document:** Phase 07 of Version 1.01
**Authority:** Stage 6 — Master Versioned Implementation Roadmap
**Date:** 2026-06-27

---

## Objective

Establish the feature-module architecture for the frontend before any feature code is written. Define conventions, create templates, build shared utilities, and verify that the module system works with lazy loading and independent loading.

---

## Purpose

P04 created the feature module directories. P07 fills them with a repeatable architecture: every new feature in v1.03+ follows the same template, same conventions, same dependency rules. This eliminates ad-hoc component placement and ensures features are independently loadable, testable, and removable.

Without P07, every future feature implementation would need to make architectural decisions about where to put code, how to structure exports, and how to handle shared dependencies. P07 pre-decides these.

## Implementation Tasks

### Task 1: Create Feature Module Template

Create the canonical template that every feature module follows. This is the "skeleton" that future feature implementations copy and fill.

**Target structure per feature module:**

```
frontend/src/features/<feature>/
├── index.ts              # Public API — the ONLY file other features import from
├── types.ts              # Feature-scoped TypeScript types and interfaces
├── api.ts                # Feature-scoped API wrappers (thin layer over shared/api/)
├── components/
│   ├── index.ts          # Re-exports all components for internal use
│   └── <FeatureName>.tsx # Main feature component
├── hooks/
│   ├── index.ts          # Re-exports all hooks
│   └── use<Feature>.ts   # Feature-scoped hooks
└── __tests__/
    ├── <feature>.test.ts # Unit tests
    └── fixtures.ts       # Test fixtures for this feature
```

**Files to create for each feature module:**

| File | Content | Notes |
|------|---------|-------|
| `index.ts` | Barrel exports from `components/`, `hooks/`, `types.ts` | **Public contract** — only import path for other features |
| `types.ts` | TypeScript interfaces and types for the feature | No runtime dependencies, pure type definitions |
| `api.ts` | Thin wrappers around `shared/api/` calls with feature-specific error handling | Imports from `@/shared/api` only |
| `components/index.ts` | `export { default as X } from './X'` for each component | Internal barrel |
| `hooks/index.ts` | `export { useX } from './useX'` for each hook | Internal barrel |
| `__tests__/fixtures.ts` | Mock data factories for the feature's types | Used by feature tests and integration tests |

**Example — `memory` feature module template:**

```typescript
// frontend/src/features/memory/index.ts
// Memory Feature Module — Public API
// All other features import from this file only.

export { MemoryView } from './components';
export { useMemorySearch, useMemoryStats } from './hooks';
export type { MemoryItem, MemorySearchResult, MemoryStats } from './types';

// Feature metadata (used by feature registration)
export const MEMORY_FEATURE = {
  id: 'memory',
  name: 'Memory',
  description: 'Long-term memory management and search',
  routes: ['/memory', '/memory/search'],
  sidebarOrder: 1,
} as const;
```

```typescript
// frontend/src/features/memory/types.ts
// Memory Feature — Type Definitions

export interface MemoryItem {
  id: string;
  content: string;
  metadata: Record<string, unknown>;
  createdAt: string;
  updatedAt: string;
}

export interface MemorySearchResult {
  item: MemoryItem;
  score: number;
  highlights: string[];
}

export interface MemoryStats {
  totalItems: number;
  totalSize: number;
  lastIndexed: string;

```

```typescript
// frontend/src/features/memory/api.ts

// Thin wrappers over shared API client with feature-specific error handling.

import { apiClient } from '@/shared/api/client';
import type { MemoryItem, MemorySearchResult, MemoryStats } from './types';

export async function searchMemory(query: string): Promise<MemorySearchResult[]> {
  const response = await apiClient.get('/api/v1/memory/search', {
    params: { q: query },
  });
  return response.data;
}

export async function getMemoryStats(): Promise<MemoryStats> {
  const response = await apiClient.get('/api/v1/memory/stats');
  return response.data;
}
```

### Task 2: Define Feature Module Conventions

Create a conventions document that governs all feature module development. This is the **authoritative reference** for how to build frontend features.

**Target file:** `frontend/src/features/CONVENTIONS.md`

**Conventions to define:**

```markdown
# Feature Module Conventions — CORTEX Frontend

## Naming Conventions

| Item | Convention | Example |
|------|-----------|---------|
| Directory | lowercase singular | `memory/`, `search/`, `agents/` |
| Component files | PascalCase | `MemoryView.tsx`, `SearchResults.tsx` |
| Hook files | camelCase with `use` prefix | `useMemorySearch.ts` |
| Type files | camelCase | `types.ts` |
| API files | camelCase | `api.ts` |
| Test files | `<name>.test.ts` | `useMemorySearch.test.ts` |
| Fixture files | `fixtures.ts` | `fixtures.ts` |

## Export Rules

1. **Public API:** `index.ts` is the ONLY file other features import from.
2. **Internal imports:** Features may import from `@/shared/` but NOT from other `@/features/*/` directories.
3. **Type imports:** Always use `import type { X }` for type-only imports.
4. **Re-exports:** `index.ts` re-exports everything consumers need. No deep imports.

## Dependency Rules

1. **Features depend on shared, never on each other.** `features/memory/` cannot import from `features/search/`.
2. **Shared is the integration layer.** If two features need to share data, it goes in `shared/`.
3. **No circular dependencies.** Feature → Shared → Feature is forbidden.
4. **API layer isolation:** Feature `api.ts` wraps `shared/api/` calls. Features never call `apiClient` directly.

## File Structure Rules

1. **Minimum files per feature:** `index.ts`, `types.ts`, `api.ts` (3 files).
2. **Components directory:** Required if feature has UI. Empty `components/index.ts` if no components yet.
3. **Hooks directory:** Required if feature has state logic. Empty `hooks/index.ts` if no hooks yet.
4. **Tests directory:** Required. At minimum, a smoke test that verifies the feature module loads.

## Lazy Loading

1. **Every feature module is lazy-loaded** via `React.lazy()` in the router.
2. **Route definition** imports from `@/features/<feature>/index.ts`.
3. **No feature is eagerly imported** in the root layout (except shared providers).

## Code Style

1. **Functional components only** — no class components.
2. **Hooks for state** — no raw `useState` in components deeper than 1 level.
3. **Error boundaries** — each feature wraps its route in an error boundary.
4. **Suspense** — each lazy-loaded feature shows a skeleton during loading.
```

**Test Criteria:**
- `CONVENTIONS.md` exists at `frontend/src/features/CONVENTIONS.md`
- Document covers all 7 convention sections
- Examples are correct TypeScript/React

**Risk Notes:**
- *Risk:* Conventions are too rigid. *Mitigation:* Document exceptions explicitly. "If a rule needs breaking, add an exception entry."
- *Risk:* Conventions are ignored. *Mitigation:* P07 Task 5 (validation) checks conventions. Future CI can lint convention compliance.

Move existing frontend components from the flat `shared/` structure to appropriate feature modules or keep them in `shared/` if they are genuinely cross-cutting.

**Current state:** P04 created feature module directories. Existing components still live in `shared/components/`.

|-----------------|--------|-----------|
| `shared/components/Layout.tsx` | `shared/components/Layout.tsx` (stays) | Cross-cutting — used by all features |
| `shared/components/Sidebar.tsx` | `shared/components/Sidebar.tsx` (stays) | Cross-cutting — navigation chrome |
| `shared/components/Header.tsx` | `shared/components/Header.tsx` (stays) | Cross-cutting — app chrome |
| `shared/components/NeuralNetwork.tsx` | `shared/components/NeuralNetwork.tsx` (stays) | Cross-cutting — background |
| `shared/components/ChatMessage.tsx` | `features/conversations/components/ChatMessage.tsx` | Domain-specific |
| `shared/components/SearchResults.tsx` | `features/search/components/SearchResults.tsx` | Domain-specific |

| `shared/components/ModelCard.tsx` | `shared/components/ModelCard.tsx` (stays) | Used by multiple features |

**Shared components (stay in `shared/components/`):**
- Layout, Sidebar, Header, Navigation — app chrome
- NeuralNetwork — decorative background
- ModelCard, Button, Input, Modal, Toast — UI primitives
- ErrorBoundary, SuspenseWrapper — cross-cutting concerns

**Migration steps:**

1. Create `shared/components/index.ts` that re-exports all shared components
2. Move domain-specific components to feature modules (git mv)
3. Update imports in all consumers
4. Verify build passes after each move

**Import pattern change:**

```typescript
// Before

// After
import { ChatMessage } from '@/features/conversations';
// Or for internal use within the feature:
import { ChatMessage } from './components/ChatMessage';
```

**Test Criteria:**
- All domain-specific components moved to feature modules
- All shared components remain in `shared/components/`
- `npm run build` succeeds
- No component is in both `shared/` and a feature module
- `grep -rn "from '@/shared/components/ChatMessage'" frontend/src/` returns 0 results (moved component)

**Risk Notes:**
- *Risk:* Moving a component breaks multiple consumers. *Mitigation:* Move one component at a time, build after each move.
- *Risk:* Circular dependency after move (feature imports shared, shared imports feature). *Mitigation:* Shared never imports from features. Verify with import analysis.
- *Risk:* Moving too many components at once. *Mitigation:* Prioritize by usage count — move most-used first, least-used last.

**Example — `useApiCall` hook:**

```typescript
// frontend/src/shared/hooks/useApiCall.ts
import { useState, useCallback } from 'react';
import type { ApiError } from '../types/api';

interface UseApiCallResult<T> {
  data: T | null;
  loading: boolean;
  error: ApiError | null;
  execute: () => Promise<void>;
  refetch: () => Promise<void>;
}

export function useApiCall<T>(fn: () => Promise<T>): UseApiCallResult<T> {
  const [data, setData] = useState<T | null>(null);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<ApiError | null>(null);

  const execute = useCallback(async () => {
    setLoading(true);
    setError(null);
    try {
      const result = await fn();
      setData(result);
    } catch (err) {
      setError({
        code: 'UNKNOWN',
        message: err instanceof Error ? err.message : 'Unknown error',
      });
    } finally {
      setLoading(false);
    }
  }, [fn]);

  return { data, loading, error, execute, refetch: execute };
}
```

**Test Criteria:**
- All shared utility files exist with valid TypeScript
- `useApiCall` hook works with a mock API function
- `classNames` handles edge cases (undefined, false, empty string)
- `debounce` actually delays execution
- `shared/types/` exports all common types
- `npm run build` succeeds
- No feature-specific code in shared utilities

**Risk Notes:**
- *Risk:* Shared utilities become dumping ground for "common" code. *Mitigation:* Only add to shared when 2+ features need it. Otherwise, keep in feature module.
- *Risk:* Shared hooks create coupling. *Mitigation:* Hooks are stateless adapters. They don't know about features.

  exit 1
fi
echo "PASS: No cross-feature imports"

# Check 3: All index.ts files exist
echo "Checking index.ts files..."
for dir in $EXPECTED_DIRS; do
  if [ ! -f "src/features/$dir/index.ts" ] && [ ! -f "src/features/$dir/index.tsx" ]; then
    echo "FAIL: Missing index.ts in src/features/$dir"

  fi
done
echo "PASS: All index.ts files exist"

# Check 4: TypeScript compiles
echo "Checking TypeScript compilation..."
npx tsc --noEmit
echo "PASS: TypeScript compiles"

echo "PASS: Build succeeds"

echo "=== All feature module checks passed ==="

### Task 6: Create Feature Registration Pattern

Establish a centralized feature registration system for routing, sidebar navigation, and feature discovery.

**Target file:** `frontend/src/features/registry.ts`

```typescript
// frontend/src/features/registry.ts
// Feature Registry — Centralized feature registration for routing and navigation.
// Each feature module exports a FEATURE constant. This file aggregates them.

import { lazy } from 'react';
import type { ComponentType, LazyExoticComponent } from 'react';

export interface FeatureMetadata {
  id: string;
  name: string;
  description: string;
  icon?: string;
  routes: Array<{
    path: string;
    label: string;
  }>;
  sidebarOrder: number;
  enabled: boolean;
}

export interface RegisteredFeature extends FeatureMetadata {
  component: LazyExoticComponent<ComponentType>;
}

// Lazy-loaded feature components
const LazyMemory = lazy(() => import('./memory'));
const LazyAwareness = lazy(() => import('./awareness'));
const LazyConversations = lazy(() => import('./conversations'));
const LazyRepositories = lazy(() => import('./repositories'));
const LazyDocuments = lazy(() => import('./documents'));
const LazySearch = lazy(() => import('./search'));
const LazyAgents = lazy(() => import('./agents'));
const LazyNotifications = lazy(() => import('./notifications'));
const LazySettings = lazy(() => import('./settings'));
const LazySystem = lazy(() => import('./system'));
const LazyUtility = lazy(() => import('./utility'));
const LazyIntegration = lazy(() => import('./integration'));

// Feature registry — single source of truth for all features
export const FEATURES: RegisteredFeature[] = [
  {
    id: 'memory',
    name: 'Memory',
    description: 'Long-term memory management and search',
    routes: [{ path: '/memory', label: 'Memory' }],
    sidebarOrder: 1,
    enabled: true,
    component: LazyMemory,
  },
  {
    id: 'awareness',
    name: 'Awareness',
    description: 'File system awareness and indexing',
    routes: [{ path: '/awareness', label: 'Awareness' }],
    sidebarOrder: 2,
    enabled: true,
    component: LazyAwareness,
  },
  // ... other features follow same pattern
];

// Utility functions
export function getFeatureById(id: string): RegisteredFeature | undefined {
  return FEATURES.find(f => f.id === id);
}

export function getEnabledFeatures(): RegisteredFeature[] {
  return FEATURES.filter(f => f.enabled);
}

export function getSidebarFeatures(): RegisteredFeature[] {
  return getEnabledFeatures()
    .sort((a, b) => a.sidebarOrder - b.sidebarOrder);
}

export function getRoutes(): Array<{ path: string; component: LazyExoticComponent<ComponentType> }> {
  return getEnabledFeatures().flatMap(feature =>
    feature.routes.map(route => ({
      path: route.path,
      component: feature.component,
    }))
  );
}
```

**Router integration:**

Update the main router to use the registry:

```typescript
// frontend/src/app/router.tsx (or equivalent)

function LoadingFallback() {
  return <div className="animate-pulse bg-glass rounded-lg h-64" />;
}

export function AppRouter() {
  const routes = getRoutes();

  return (
    <Suspense fallback={<LoadingFallback />}>
      {/* Routes generated from feature registry */}
      {routes.map(({ path, component: Component }) => (
        <Route key={path} path={path} element={<Component />} />
      ))}
    </Suspense>
  );
}
```

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Template over-engineering | Low | Keep minimal — structure only, no logic |
| Conventions ignored by future contributors | Medium | Validation script catches violations; CI can enforce |
| Component migration breaks consumers | Medium | Move one component at a time, build after each |
| Feature registry becomes stale | Medium | Registry is single source of truth; adding feature requires registry update |
| Lazy loading adds complexity | Low | React.lazy is standard; error boundaries catch failures |
| Shared utilities become dumping ground | Low | Only add when 2+ features need it; keep minimal |
