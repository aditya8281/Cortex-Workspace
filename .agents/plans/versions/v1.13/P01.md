## Architecture Decisions

### ADR-13-01: Utility Model Ownership Pattern

**Decision:** All utility models use `user_id` integer foreign key to the users table, matching the existing ownership pattern from earlier versions.

**Rationale:** Consistent with the ownership check pattern (`resource.user_id == current_user.id`) enforced on all user-scoped endpoints. SQLite testing uses integer IDs.

**Consequence:** No polymorphic ownership. Each utility type is independently user-scoped. Cross-domain linking (e.g., task → calendar event) uses integer references within the same user scope.

### ADR-13-02: JSON Fields for Flexible Data

**Decision:** Use SQLAlchemy `JSON` type (mapped to `JSONB` in PostgreSQL, `JSON` in SQLite via conftest compilation) for semi-structured data like recurrence rules, extension configs, sync metadata, and workspace settings.

**Rationale:** These fields have variable schemas that evolve across versions. JSON allows schema flexibility without migrations for every new property.

**Consequence:** No database-level validation for JSON fields. Validation happens at the Pydantic schema level. Queries on JSON fields use PostgreSQL JSONB operators (with SQLite fallback for tests).

### ADR-13-03: Version History as Separate Table

**Decision:** Document version history is a separate `document_versions` table, not embedded JSON in the documents table.

**Rationale:** Version history can grow unbounded. Separate table allows independent cleanup, indexing, and pagination. Matches the existing pattern for entity versioning.

**Consequence:** JOIN required for latest-version queries. Mitigated by a `current_version` column on `documents` that caches the latest version number.

### Task 1: Create Calendar Event Model

**File:** `backend/app/models/utility/calendar_event.py`

```python
from sqlalchemy import Column, Integer, String, DateTime, Text, JSON, Boolean, Index
from datetime import datetime
from backend.app.db.base import Base


class CalendarEvent(Base):
    __tablename__ = "calendar_events"

    id = Column(Integer, primary_key=True, autoincrement=True)
    user_id = Column(Integer, nullable=False, index=True)
    title = Column(String(500), nullable=False)
    description = Column(Text, default="")
    start_time = Column(DateTime, nullable=False)
    end_time = Column(DateTime, nullable=True)
    all_day = Column(Boolean, default=False)
    location = Column(String(500), default="")
    recurrence = Column(String(100), nullable=True)  # RRULE string (RFC 5545)
    recurrence_end = Column(DateTime, nullable=True)
    reminder_minutes = Column(Integer, nullable=True)  # Minutes before event
    timezone = Column(String(50), default="UTC")
    status = Column(String(20), default="confirmed")  # confirmed, tentative, cancelled
    visibility = Column(String(20), default="default")  # default, private, public
    external_id = Column(String(500), nullable=True)  # CalDAV/iCal UID
    external_source = Column(String(100), nullable=True)  # caldav, google, outlook
    metadata = Column(JSON, default=dict)  # Extensible properties
    created_at = Column(DateTime, default=datetime.utcnow)
    updated_at = Column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)

    __table_args__ = (
        Index("idx_calendar_user_start", "user_id", "start_time"),
        Index("idx_calendar_user_end", "user_id", "end_time"),
        Index("idx_calendar_external", "external_id", "external_source"),
    )
```

**Design rationale:**
- `recurrence` stores RFC 5545 RRULE strings (e.g., `FREQ=WEEKLY;BYDAY=MO,WE,FR`)
- `external_id` + `external_source` enables CalDAV sync without duplication
- `visibility` enables private events that don't appear in shared views
- `metadata` is a JSON escape hatch for future properties without migrations
- Composite index on `(user_id, start_time)` supports the most common query pattern: "show me my upcoming events"

**Risk:** RRULE parsing complexity. **Mitigation:** Store as string, parse in service layer. Use `python-dateutil` or `rrule` library for parsing.

**Performance:** The composite index on `(user_id, start_time)` supports range queries efficiently. For users with 10K+ events, consider partitioning by month (deferred to v1.15 if needed).

**Design rationale:**

- `project_id` links tasks to workspace projects without hard coupling
- `estimated_minutes` / `actual_minutes` enables productivity analytics for dashboard
- `tags` as JSON array enables flexible categorization without a join table
- Composite index on `(user_id, status)` is the primary query pattern: "show my pending tasks"

**Risk:** Recursive subtask queries could be slow. **Mitigation:** Limit nesting depth to 5. Use recursive CTEs only for the task tree view endpoint.

**Performance:** `(user_id, status)` index covers the most common filter. `(user_id, due_date)` covers "overdue" and "upcoming" queries.

### Task 10: Create Pydantic Schemas

**File:** `backend/app/schemas/utility/calendar_event.py`

```python
from pydantic import BaseModel, Field, field_validator
from datetime import datetime
from typing import Optional, List
import re


class CalendarEventCreate(BaseModel):
    title: str = Field(..., min_length=1, max_length=500)
    description: Optional[str] = ""
    start_time: datetime
    end_time: Optional[datetime] = None
    all_day: bool = False
    location: Optional[str] = ""
    recurrence: Optional[str] = None
    reminder_minutes: Optional[int] = Field(None, ge=0, le=1440)
    timezone: str = "UTC"
    status: str = Field("confirmed", pattern="^(confirmed|tentative|cancelled)$")
    visibility: str = Field("default", pattern="^(default|private|public)$")

    @field_validator("end_time")
    @classmethod
    def end_after_start(cls, v, info):
        if v and "start_time" in info.data and v < info.data["start_time"]:
            raise ValueError("end_time must be after start_time")
        return v

    @field_validator("recurrence")
    @classmethod
    def valid_rrule(cls, v):
        if v and not re.match(r"^FREQ=", v):
            raise ValueError("recurrence must be a valid RRULE string")
        return v
```

## Per-Task Risk Analysis

| Task | Risk | Probability | Impact | Mitigation |
|------|------|------------|--------|------------|
| T1: CalendarEvent | RRULE parsing complexity | Medium | Low | Store as string, parse in service. Use `python-dateutil.rrule`. |
| T2: Task | Recursive subtask queries slow | Low | Medium | Limit nesting to 5. Index on parent_id. |
| T3: Note | GIN index not available in SQLite tests | High | Low | PostgreSQL tests for FTS, SQLite tests for CRUD. |
| T4: Document | Large file extraction timeout | Medium | Medium | Background task extraction. Status field for pending. |
| T5: Contact | CardDAV sync complexity | High | Low | P01 is models only. Sync implementation is P04/P05. |

| T7: Habit/Focus | Complex completion tracking | Low | Low | JSON array for completions. Service layer handles streak logic. |
| T8: Extension/Sync/Webhook | Schema evolution for extensions | Medium | Medium | JSON config field allows extension-specific settings without migrations. |
| T9: Workspace | Multi-workspace data isolation | Low | Medium | Workspace ID on linked entities, not a hard boundary. |
| T10: Schemas | Validation rules may be too strict | Low | Low | Use `Optional` liberally. Validators are soft (raise ValueError, not crash). |
| T11: __init__.py | Import errors on missing modules | Low | Low | Run `python -c "from backend.app.models.utility import *"` after creation. |
| T12: Migration | Downgrade fails on dependent data | Medium | High | Test downgrade on clean DB. No data to lose in P01. |
