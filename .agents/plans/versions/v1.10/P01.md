### Task 1: Create Goal Model with Hierarchical Support

**Architecture:** Goals support parent-child relationships for sub-goal decomposition. The `parent_goal_id` foreign key enables tree structures. Progress is a float 0.0-1.0, auto-computed from child goal completion when children exist. The `owner_id` field links to the user table with ownership checks on all queries.

**DB Schema:**
```sql
CREATE TABLE goals (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    title VARCHAR(500) NOT NULL,
    description TEXT,
    status VARCHAR(50) DEFAULT 'active' CHECK(status IN ('active', 'completed', 'abandoned', 'paused')),
    priority INTEGER DEFAULT 5 CHECK(priority BETWEEN 1 AND 10),
    progress FLOAT DEFAULT 0.0 CHECK(progress BETWEEN 0.0 AND 1.0),
    parent_goal_id INTEGER REFERENCES goals(id),
    deadline DATETIME,
    metadata JSON DEFAULT '{}',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    completed_at DATETIME
);
CREATE INDEX idx_goals_owner_status ON goals(owner_id, status);
CREATE INDEX idx_goals_parent ON goals(parent_goal_id);
CREATE INDEX idx_goals_deadline ON goals(deadline) WHERE deadline IS NOT NULL;
```

**File:** `backend/app/models/cognition/goal.py`
```python
from sqlalchemy import Column, Integer, String, DateTime, JSON, Text, Float, ForeignKey
from sqlalchemy.orm import relationship
from datetime import datetime
from backend.app.db.base import Base


class Goal(Base):
    __tablename__ = "goals"

    id = Column(Integer, primary_key=True, autoincrement=True)
    owner_id = Column(Integer, ForeignKey("users.id"), nullable=False, index=True)
    title = Column(String(500), nullable=False)
    description = Column(Text)
    status = Column(String(50), default="active", nullable=False)  # active, completed, abandoned, paused
    priority = Column(Integer, default=5)  # 1-10, higher = more important
    progress = Column(Float, default=0.0)  # 0.0-1.0
    parent_goal_id = Column(Integer, ForeignKey("goals.id"), index=True)
    deadline = Column(DateTime)
    metadata_ = Column("metadata", JSON, default=dict)
    created_at = Column(DateTime, default=datetime.utcnow)
    updated_at = Column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)
    completed_at = Column(DateTime)

    # Relationships
    children = relationship("Goal", back_populates="parent", lazy="selectin")
    parent = relationship("Goal", back_populates="children", remote_side=[id])
```

**Risk:** Self-referential FK may cause issues with SQLite. **Mitigation:** Test migration on SQLite first, verify no circular references possible via application-level validation.

### Task 2: Create Decision Model with What-If Support

**Architecture:** Decisions capture structured choice records with weighted options, reasoning chains, and outcome tracking. The `options` JSON field stores an array of option objects with pros/cons/scores. The `what_if_scenarios` field enables scenario comparison. Decision outcomes feed back into learning engine.

**DB Schema:**
```sql
CREATE TABLE decisions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    question TEXT NOT NULL,
    context JSON DEFAULT '{}',
    options JSON NOT NULL DEFAULT '[]',
    selected_option VARCHAR(500),
    reasoning TEXT,
    confidence FLOAT DEFAULT 0.0,
    what_if_scenarios JSON DEFAULT '[]',
    outcome VARCHAR(50) DEFAULT 'pending' CHECK(outcome IN ('pending', 'good', 'bad', 'mixed')),
    outcome_notes TEXT,
    decided_at DATETIME,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_decisions_owner ON decisions(owner_id);
CREATE INDEX idx_decisions_outcome ON decisions(outcome);
```

### Task 3: Create Plan and PlanStep Models

**Architecture:** Plans decompose objectives into ordered steps with dependencies. Each plan has a status machine: draft → active → completed/failed/cancelled. Steps have individual status tracking and dependency edges enable DAG execution.

**DB Schema:**
```sql
CREATE TABLE plans (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    objective TEXT NOT NULL,
    description TEXT,
    status VARCHAR(50) DEFAULT 'draft' CHECK(status IN ('draft', 'active', 'completed', 'failed', 'cancelled')),
    complexity VARCHAR(50) DEFAULT 'medium',
    estimated_duration_minutes INTEGER,
    actual_duration_minutes INTEGER,
    metadata JSON DEFAULT '{}',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    completed_at DATETIME
);

CREATE TABLE plan_steps (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    plan_id INTEGER NOT NULL REFERENCES plans(id) ON DELETE CASCADE,
    step_order INTEGER NOT NULL,
    action TEXT NOT NULL,
    step_type VARCHAR(100),
    status VARCHAR(50) DEFAULT 'pending' CHECK(status IN ('pending', 'running', 'completed', 'failed', 'skipped')),
    result JSON,
    error_message TEXT,
    depends_on INTEGER REFERENCES plan_steps(id),
    estimated_minutes INTEGER,
    actual_minutes INTEGER,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    completed_at DATETIME
);
CREATE INDEX idx_plan_steps_plan ON plan_steps(plan_id);
CREATE INDEX idx_plan_steps_depends ON plan_steps(depends_on);
```

### Task 4: Create ScheduledTask Model with Cron Support

**Architecture:** Scheduled tasks support one-time, interval-based, and cron expression scheduling. The `cron_expression` field stores standard 5-field cron syntax. The `timezone` field enables timezone-aware scheduling. Recurrence rules follow RFC 5545 RRULE subset.

**DB Schema:**
```sql
CREATE TABLE scheduled_tasks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    task_name VARCHAR(200) NOT NULL,
    task_type VARCHAR(100) NOT NULL,
    parameters JSON DEFAULT '{}',
    schedule VARCHAR(200) NOT NULL,
    cron_expression VARCHAR(100),
    timezone VARCHAR(50) DEFAULT 'UTC',
    next_run DATETIME,
    last_run DATETIME,
    run_count INTEGER DEFAULT 0,
    max_runs INTEGER,
    status VARCHAR(50) DEFAULT 'pending' CHECK(status IN ('pending', 'running', 'completed', 'failed', 'paused')),
    enabled INTEGER DEFAULT 1,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_scheduled_tasks_next_run ON scheduled_tasks(next_run, status) WHERE enabled = 1;
CREATE INDEX idx_scheduled_tasks_owner ON scheduled_tasks(owner_id);
```

### Task 5: Create ExecutionHistory Model with Audit Trail

**Architecture:** Every tool invocation, workflow step, and plan execution is logged with full input/output capture, duration tracking, and rollback capability flag. The `rollback_available` field is set to 1 only for operations that support safe rollback. The `parent_execution_id` enables workflow step traceability.

**DB Schema:**
```sql
CREATE TABLE execution_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    operation VARCHAR(200) NOT NULL,
    operation_type VARCHAR(100) NOT NULL,
    parent_execution_id INTEGER REFERENCES execution_history(id),
    input_data JSON,
    output_data JSON,
    status VARCHAR(50) DEFAULT 'running' CHECK(status IN ('running', 'success', 'failed', 'rolled_back', 'cancelled')),
    duration_ms INTEGER,
    error_message TEXT,
    rollback_available INTEGER DEFAULT 0,
    started_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    completed_at DATETIME
);
CREATE INDEX idx_execution_history_owner ON execution_history(owner_id);
CREATE INDEX idx_execution_history_type_status ON execution_history(operation_type, status);
CREATE INDEX idx_execution_history_parent ON execution_history(parent_execution_id);
CREATE INDEX idx_execution_history_started ON execution_history(started_at DESC);
```

### Task 6: Create RecoveryPoint Model

**Architecture:** Recovery points capture state snapshots before operations that modify state. The `state_snapshot` JSON stores the complete pre-operation state. The `recovery_action` defines what to do on recovery: rollback (undo), retry (re-execute), or skip (mark as completed). Recovery points are created before each rollbackable operation and cleaned up after successful completion.

**DB Schema:**
```sql
CREATE TABLE recovery_points (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    execution_id INTEGER NOT NULL REFERENCES execution_history(id),
    state_snapshot JSON NOT NULL DEFAULT '{}',
    recovery_action VARCHAR(50) NOT NULL DEFAULT 'rollback',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_recovery_points_execution ON recovery_points(execution_id);
```

**File:** `backend/app/models/execution/recovery_point.py`
```python

    execution_id = Column(Integer, ForeignKey("execution_history.id"), nullable=False, index=True)
    state_snapshot = Column(JSON, nullable=False, default=dict)
```
