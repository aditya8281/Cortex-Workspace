## Implementation Tasks

### Task 1: Create VoiceRecord Model

**Architecture:** Voice records store audio file paths, transcripts, language metadata, and processing status. The `audio_path` references encrypted storage via the vault system. The `duration_ms` field tracks audio length for performance monitoring. The `confidence` field stores STT confidence score (0.0-1.0). Processing status: pending → processing → completed/failed.

**DB Schema:**
```sql
CREATE TABLE voice_records (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    audio_path VARCHAR(1000) NOT NULL,
    transcript TEXT,
    language VARCHAR(10) DEFAULT 'en',
    duration_ms INTEGER,
    confidence FLOAT,
    processing_status VARCHAR(50) DEFAULT 'pending',
    metadata JSON DEFAULT '{}',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    processed_at DATETIME
);
CREATE INDEX idx_voice_records_owner ON voice_records(owner_id);
CREATE INDEX idx_voice_records_created ON voice_records(created_at DESC);
```

**File:** `backend/app/models/interaction/voice_record.py`
```python
from sqlalchemy import Column, Integer, String, DateTime, Text, Float, JSON, ForeignKey
from datetime import datetime
from backend.app.db.base import Base


class VoiceRecord(Base):
    __tablename__ = "voice_records"

    id = Column(Integer, primary_key=True, autoincrement=True)
    owner_id = Column(Integer, ForeignKey("users.id"), nullable=False, index=True)
    audio_path = Column(String(1000), nullable=False)
    transcript = Column(Text)
    language = Column(String(10), default="en")
    duration_ms = Column(Integer)
    confidence = Column(Float)
    processing_status = Column(String(50), default="pending")  # pending, processing, completed, failed
    metadata_ = Column("metadata", JSON, default=dict)
    created_at = Column(DateTime, default=datetime.utcnow)
    processed_at = Column(DateTime)
```

**Security:** Audio files stored encrypted via vault. Transcript may contain sensitive data — encrypted at rest. Processing status tracked for retry logic.

### Task 2: Create CommandPalette Model

**Architecture:** Command palette stores registered commands with usage analytics. The `usage_count` field enables popular command ranking. The `shortcut` field stores keyboard shortcut strings (e.g., "Ctrl+Shift+S"). Categories group commands for UI organization. Custom commands support user-defined actions.

**DB Schema:**
```sql
CREATE TABLE command_palette (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    command_name VARCHAR(200) NOT NULL,
    description TEXT,
    shortcut VARCHAR(50),
    category VARCHAR(100) DEFAULT 'general',
    action_type VARCHAR(100) DEFAULT 'builtin',
    action_params JSON DEFAULT '{}',
    usage_count INTEGER DEFAULT 0,
    last_used DATETIME,
    enabled INTEGER DEFAULT 1,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_command_palette_owner ON command_palette(owner_id);
CREATE INDEX idx_command_palette_category ON command_palette(owner_id, category);
```

### Task 3: Create ProactiveSuggestion Model

**Architecture:** Proactive suggestions are generated by the awareness engine and contextual analysis. Each suggestion has a confidence score, expiration time, and acceptance tracking. Suggestions are filtered by confidence threshold and expiration before display. The `context` field stores the trigger context for analytics.

**DB Schema:**
```sql
CREATE TABLE proactive_suggestions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    suggestion_type VARCHAR(100) NOT NULL,
    title VARCHAR(500) NOT NULL,
    description TEXT,
    context VARCHAR(500),
    confidence FLOAT DEFAULT 0.5,
    accepted INTEGER,  -- NULL=pending, 1=accepted, 0=dismissed
    metadata JSON DEFAULT '{}',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    expires_at DATETIME,
    responded_at DATETIME
);
CREATE INDEX idx_proactive_suggestions_owner ON proactive_suggestions(owner_id);
CREATE INDEX idx_proactive_suggestions_active ON proactive_suggestions(owner_id, expires_at)
    WHERE accepted IS NULL;
```

### Task 4: Create ConversationSummary Model

**Architecture:** Conversation summaries store compressed representations of conversation sessions. The `compression_ratio` tracks summary quality (original_words / summary_words). The `key_points` JSON stores extracted key topics. The `embedding_id` references the vector store entry for semantic retrieval.

**DB Schema:**
```sql
CREATE TABLE conversation_summaries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    session_id INTEGER,
    summary TEXT NOT NULL,
    key_points JSON DEFAULT '[]',
    topics VARCHAR(500),
    word_count_original INTEGER,
    compression_ratio FLOAT,
    embedding_id VARCHAR(100),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_conversation_summaries_owner ON conversation_summaries(owner_id);
CREATE INDEX idx_conversation_summaries_session ON conversation_summaries(session_id);
```

### Task 5: Create FeedbackEntry Model

**Architecture:** Feedback entries capture user responses to features and interactions. The `rating` field (1-5) enables satisfaction scoring. The `feature` field links feedback to specific capabilities. The `sentiment` field stores computed sentiment (-1.0 to 1.0). Feedback drives improvement suggestions in the learning engine.

**DB Schema:**
```sql
CREATE TABLE feedback_entries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    feature VARCHAR(200) NOT NULL,
    rating INTEGER CHECK(rating BETWEEN 1 AND 5),
    comment TEXT,
    sentiment FLOAT,
    interaction_id INTEGER,
    metadata JSON DEFAULT '{}',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_feedback_entries_owner ON feedback_entries(owner_id);
CREATE INDEX idx_feedback_entries_feature ON feedback_entries(feature);
```

### Task 6: Create ConversationMemory Model

**Architecture:** Conversation memory stores structured conversation state across sessions. The `embedding_id` references vector store for semantic search. The `context_window` JSON stores recent messages for continuity. The `summary_id` links to compressed representation.

**DB Schema:**
```sql
CREATE TABLE conversation_memory (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),

    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP

CREATE INDEX idx_conversation_memory_owner ON conversation_memory(owner_id);
```

### Task 7: Create DeviceRegistry and SyncState Models

**Architecture:** Multi-device sync requires device registration and state synchronization. The `device_registry` tracks connected devices with capabilities. The `sync_state` tracks per-device sync status with conflict resolution metadata. Conflict resolution uses last-writer-wins for metadata and CRDT-like merge for structured data.

**DB Schema:**
```sql
CREATE TABLE device_registry (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users.id,
    device_name VARCHAR(200) NOT NULL,
    device_type VARCHAR(100),
    capabilities JSON DEFAULT '[]',
    last_seen DATETIME,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE sync_state (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES users(id),
    device_id INTEGER REFERENCES device_registry(id),
    entity_type VARCHAR(100) NOT NULL,
    entity_id INTEGER NOT NULL,
    version INTEGER DEFAULT 1,
    checksum VARCHAR(64),
    last_synced DATETIME,
    conflict_count INTEGER DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_sync_state_entity ON sync_state(entity_type, entity_id);
CREATE INDEX idx_sync_state_device ON sync_state(device_id);
```
